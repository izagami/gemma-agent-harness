# srv-db01 の通信ポリシー（2026-10 改訂）

サーバー: IPv4 `10.0.20.10`、IPv6 `2001:db8:20::10`。インターフェースは `lo` と `eth0`。
**IPv4 と IPv6 で、まったく同じポリシーを適用します。**

| 名前 | IPv4 | IPv6 |
|---|---|---|
| 管理用 VLAN | 10.0.10.0/24 | 2001:db8:10::/64 |
| アプリサーバー | 10.0.30.5 | 2001:db8:30::5 |
| 社内 DNS | 10.0.0.53 | 2001:db8::53 |

## 受信（input）

1. `lo` からのパケットはすべて許可。
2. 接続状態が invalid のパケットは、ほかの規則にかかわらず捨てる（`lo` を除く）。
3. 確立済み・関連（established / related）のパケットは許可。
4. SSH（tcp/22）は管理用 VLAN からのみ。
5. HTTP / HTTPS（tcp/80, tcp/443）はどこからでも。
6. PostgreSQL（tcp/5432）はアプリサーバーからのみ。
7. ICMP（IPv4 は icmp、IPv6 は icmpv6）は、family ごとに毎秒5個まで許可し、超えた分は捨てる。
8. それ以外はすべて捨てる。

## 送信（output）

1. `lo` へのパケットはすべて許可。
2. 接続状態が invalid のパケットは捨てる（`lo` を除く）。
3. 確立済み・関連のパケット（受け付けた接続への応答など）は許可。
4. 新しい接続は次だけを許可する: 社内 DNS への DNS（udp/53, tcp/53）、どこへでも NTP（udp/123）、どこへでも HTTPS（tcp/443）。
5. それ以外はすべて捨てる。

一時的な許可（業者の作業用など）は、作業が終わったら必ず消すこと。

## 監査報告（audit/report.json）

ルールのポリシー違反を見つけたら、次の形式で1件ずつ書きます。

    {"violations": [{"id": "<ルールID、集合名、またはチェイン名>", "kind": "<種類>", "detail": "<説明>"}]}

`id` は、問題の原因になっているルールの ID（例 `in4-03`）。集合の中身が原因なら集合名（例 `admin4`）。チェインに規則が足りない・チェインそのものが無いときはチェイン名（無いチェインは、ほかのチェインの命名にならった名前。例 `input4` に対する `input6`）。
`kind` は次のどれか:

- `shadowing`: 前にある広いルールのせいで、後ろのルールで意図した制限が効いていない。
- `wide_cidr`: アドレスの範囲がポリシーより広い。
- `debug_rule`: ポリシーにない一時的な許可が残っている。
- `missing_state`: 確立済み・関連のパケットの扱いが欠けている。
- `missing_chain`: family と hook の組み合わせにチェインが無く、まったく絞り込まれていない。
